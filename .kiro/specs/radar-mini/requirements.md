# Requirements — SP500 Valuation Radar Mini

Status: draft v1, 2026-11-10. Scope is fixed by PLAN.md (approved 2026-11-10);
anything not listed here is out of scope for v1.

## Introduction

Radar Mini is a self-hostable, open-source command-line tool that turns a
hand-maintained table of valuation anchors into a daily signal brief. For each
ticker it compares the latest daily close (Yahoo Finance, no API key) against
the anchor's trigger price and fair-value range, and classifies it into one of
four tiers: **red** (close at or below trigger), **fair-value zone** (close
inside the fair-value range), **yellow** (close within 5% above the trigger),
or **watch** (close within 20% above the trigger and in no other tier).
Everything else is **ok** and is not listed in the brief.

The tool is an information/observation aid only. It produces no orders, no
portfolio logic, and no investment advice.

## Glossary

- **Anchor**: one row of the input CSV — ticker, trigger price, fair-value
  range low/high, GICS sector, market-cap tier.
- **Close**: the most recent completed daily closing price for a ticker.
- **Tier**: the single primary classification assigned to a ticker per run.
- **Brief**: the Markdown report generated by a run.

## Requirements

### R1. Anchor input (CSV)
1. WHEN the tool starts, it SHALL read the anchor CSV whose path is given on
   the command line (default `anchors.csv`).
2. Each row SHALL contain: `ticker`, `trigger`, `fair_low`, `fair_high`,
   `sector`, `cap_tier`.
3. IF a row is malformed (missing field, non-numeric or non-positive trigger,
   `fair_low <= trigger`, `fair_high < fair_low`), THEN the run SHALL fail
   with a message naming the row — it SHALL NOT silently skip or repair it.
4. The repository SHALL ship only 5–10 large-cap **sample** anchors, clearly
   labelled as sample data. Real production anchor values SHALL NOT be
   committed.

### R2. Price retrieval
1. For each ticker the tool SHALL fetch daily closes from Yahoo Finance
   without any API key or credential.
2. Only the latest **completed** daily close SHALL be used; intraday or
   pre-market quotes SHALL NOT trigger a tier.
3. IF a ticker's price cannot be retrieved or is stale, THEN that ticker
   SHALL be reported as `no-data` in the brief's coverage note, and the brief
   SHALL state how many of the anchors were actually priced. A partial run
   SHALL NOT be presented as an all-clear.
4. Missing data SHALL fail closed: no price is ever estimated, carried
   forward silently, or filled by an AI.

### R3. Tier classification (pure function)
1. Classification SHALL be a pure, deterministic function of
   (close, trigger, fair_low) with this precedence:
   - **red**: `close <= trigger`
   - **fair-value zone**: `trigger < close <= fair_low`
   - **yellow**: `close <= trigger * 1.05`
   - **watch**: `close <= trigger * 1.20`
   - otherwise **ok**.
2. Because the fair-value zone overlaps the yellow band in the production
   methodology (where fair entry is tracked as an independent flag), the
   result SHALL also carry an `in_fair_range` boolean so no information is
   lost by the single primary tier.
3. Boundary values are inclusive exactly as written above
   (`close == trigger` is red; `close == fair_low` is fair-value zone).

### R4. Output
1. The tool SHALL print a terminal table and write a Markdown brief.
2. Every listed ticker SHALL show: ticker, close, trigger, distance to
   trigger (%), market-cap tier, and GICS sector.
3. Within each tier group, tickers SHALL be sorted by distance to trigger
   ascending; ties (within 5 percentage points) SHALL be broken by larger
   market cap first.
4. The brief SHALL include a coverage note (priced N of M anchors, list of
   `no-data` tickers) and a "not investment advice" disclaimer.

### R5. Safety and repository hygiene
1. The repository SHALL contain no API keys, no credentials, no real
  portfolio data, no production anchor values, and no personal paths.
2. The tool SHALL make no network calls other than the price fetch in R2.
3. The `/.kiro` directory SHALL be committed (never gitignored).

### R6. Testing
1. The classification function (R3) SHALL be covered by property-based
   tests, including: monotonicity (lowering the close never moves a ticker
   to a *less* severe tier), boundary inclusivity (R3.3), and mutual
   exclusivity of the primary tier.
2. CSV validation (R1.3) and the fail-closed price path (R2.3–R2.4) SHALL
   have unit tests.

## Out of scope (v1)
Portfolio/holdings, Binance or any broker integration, risk gates, sector
drawdown monitoring, dual-source price verification, AI anchor research
(L2/L3), and any web UI.
